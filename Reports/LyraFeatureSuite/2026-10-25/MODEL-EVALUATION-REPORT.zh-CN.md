## 场景：为现有 UE5 Lyra 多人射击项目扩展玩法与反馈系统

选取的具体编程场景是：在已有 UE5 Lyra 工程中完成可保存、可运行、支持多人游戏的功能扩展。它同时涉及 C++、Gameplay Ability System、蓝图、UMG 界面、数据资源、动画通知、Niagara 和网络同步，要求模型把逻辑、资源引用与游戏入口接成完整功能。

同一项目场景拆为三个独立开发任务，每题预算 45 分钟、满分 100 分。各题从冻结起点开始，不要求上一题成功，三题合计满分 300：

| 任务 | 用户能实际使用的目标行为 | 主要验收内容 |
| --- | --- | --- |
| 交互与背包 | 靠近物品出现提示，按 F 拾取，按 Tab 查看背包。 | 距离与遮挡、物品配置、多人争抢、归属隔离、重生和切图后的行为。 |
| 连杀荣誉 | 服务器识别连杀和连续击杀，在正确玩家 HUD 显示对应荣誉。 | 时间与数量阈值、消息定向、队列与替换、界面素材、异常恢复和生命周期清理。 |
| 场景效果 | 走路与落地根据地面材质播放对应声音和 Niagara。 | Notify/Trace、上下文与库匹配、蓝图职责、保存资源、动画 Modifier、编辑器预览和多人行为。 |

实际使用流程包括：让模型在独立工作区开发并交付，冻结候选后另行验收；核对干净构建、原生资源读取、保存后新进程重开、正常输入和多人运行。评分来自这些证据，模型在最终答复中自称完成不直接得分。

比较采用同一冻结题集和原评分条目。GPT-5.6 沿用同一起点、提示词与素材，35 个关键引擎文件与原三模型统一验收基线一致。客户端版本、历史修复和恢复仍有差异，下文保留这些条件，不能把四轮称为所有环境完全相同。

**未验证原因概览**

本报告基于这次本机实际开发记录和独立验收结果。任务状态、已确认分数和未验证原因分别记录：**“模型交付的前置功能没有打通”和“评测没有取得足够证据”是两种不同情况。**

- **模型交付前置未打通：** 已有证据表明必要的功能、配置或资源缺失，使后续检查不能成立。例如没有一次有效拾取，便无法检验拾取成功后的竞争去重。这反映本次交付不足，但不证明尚未测到的去重算法本身错误。
- **评测未形成有效观察：** 测试没有形成所需动作、时序或可靠取证，例如未能证明对象真正回收，或未建立受控的异步完成顺序。这是现有评测证据的缺口，不能据此判候选通过，也不能判候选失败。
- **混合原因与归因不足：** 前者同时存在候选前置和评测缺口；后者缺少足够证据确定责任。两类均单列，不强行塞入前两类，也不按比例拆分分值。

### 1.1 DeepSeek：部分完成，基础规则有效，完整交付较弱

#### 交互：12/100，部分完成，核心闭环失败

**已完成：** 保留原有移动、视角和武器行为；事件补充数据能够进入能力；交付蓝图编译、新进程资源回读及部分说明边界有通过证据。

**主要失败：**

- 从保存的测试地图进入后，真实移动和 F 操作能进入生产拾取路径，但背包对象为 `None`；Tab 能触发能力，未出现实际背包界面。
- 目标失去资格后，交互提示跨多个扫描周期仍未清理。
- Actor/ActorComponent 接收和目标 ASC 路径没有完成所要求的完整交互；无效组件仍触发接收者，空接口场景出现实际崩溃。
- 物品配置、持久化输入及 UI 资源链存在缺失；动态调整物品配置不能得到要求的实际结果。
- 多人竞争中的必要成功产出、Pawn 更换后的后续交互未通过。

**未验证边界：** 拾取和 UI 主路径不成立后，部分界面、胜者归属及后续隔离断言无法获得完整证据；这些项目保留未验证。

#### 连杀荣誉：59/100，部分完成，也是该组最强项

**已完成：** 服务器基础规则，包括连续击杀时间边界、存活连杀阈值、死亡/自杀/无攻击者重置、不同玩家独立计数；数据与蓝图资源；Elimination 和 Control Points 的实际链路；部分高档替换及公共对局回归。

**主要失败：**

- Dedicated、Listen 和本地多玩家接收隔离出现递归转发或重复通知，部分通知进入错误视图。
- 合法本地通知重放产生重复展示，无关 PlayerState 的过滤不足。该证据没有证明客户端能伪造服务器击杀或突破服务器奖励权限。
- 异常媒体资源后的恢复、HUD 清理和实际 UI 媒体表现未通过；重生或进入新世界后仍看到旧荣誉提示。
- 设计说明和可复现证据文档未满足要求。

**未验证边界：** 异步加载完成顺序与队列展示顺序仍有 4 分未验证。

#### 场景效果：23/100，部分完成，代码、资源与效果不一致

**已完成：** 部分资源库和上下文切换、角色隔离；蓝图编译；默认库有效条目、项目物理表面映射；工厂创建和新进程回读。

**主要失败：**

- 存在专用组件时，通用接口接收者被跳过；有效物理命中和表面转换条件下缺少要求的输出。
- 上下文匹配把父标签当作精确匹配，多条命中累加和重复加载处理不符合要求。
- 保存的 `B_FootStep` 分支执行线断开，下游节点不可达；命中位置和法线没有正确连接，生成位置保留默认值。
- Walk/Land 的保存标签与实际应用结果不符；第二次 Apply 后有效 ContextFX Notify 从 2 个变成 3 个，新增结果在重新打开后仍存在。
- 第二资源库虽然存在有效条目，保存的第二角色仍引用默认库；测试地面物理材质及验证资源不完整。
- 编辑器预览未得到要求的正向声效/特效；部分“已保存、已回读”的交付说明与资源实际状态不符。

**评价：** 本次 DeepSeek 能实现部分局部规则与数据结构，但“配置已保存—正常操作触发—运行结果正确”这一整条链路完成度不足。低分有大量已确认候选缺陷支撑，不能全部归因于评测环境；剩余 69 分未知仍需独立保留。

**未验证归因：** 69 分未裁定中，26 分由候选前置功能阻断，21 分是评测覆盖或取证缺口，17 分原因混合，5 分暂不能明确归因。候选前置的具体例子是生产拾取得到 Inventory=None、没有成功拾取正例，使成功后的去重和复制检查无法成立。因此，既不能把这 69 分都归给评测，也不能全部当作已确认算法错误。

### 1.2 GPT-6 Astra：部分完成，已确认完成度和覆盖率最高

#### 交互：67/100，部分完成

**已完成：** 多客户端竞争同一物品、重复请求去重、场景状态同步、背包归属隔离；遮挡和超距拒绝、提示清理、无效目标安全处理；实时背包更新、重复打开无重复广播，以及持久化资源和蓝图回读。

**主要失败：**

- 有效近距离目标在部分条件下没有出现提示。
- 完整 ActorComponent 接收路径及目标 ASC 路径未通过。
- 合法 StackCount=3 变体没有得到物品；名称/图标及物品定义变更已有成功证据，失败不能概括成所有配置变更都无效。
- 背包名称和数量布局重叠，影响查看和重新打开后的呈现；该现象不等于背包重复生成物品。
- 更换 Pawn 后交互失效；关键生产失败路径的诊断日志不足。

**未验证边界：** 交互进行中销毁目标的精确动作时序没有形成，保留 3 分未验证。

#### 连杀荣誉：77/100，部分完成

**已完成：** 基础规则、Dedicated/Listen/本地多玩家隔离、数据和 Toast 资源、两种真实对局模式、无效资源后的恢复、文档及公共回归。

**主要失败：** 通知重放产生重复展示；Relay/Host 蓝图主要作为薄转发层，将职责转入 C++，不满足任务明确要求的实质蓝图实现。

**未验证边界：** 高低档替换、异步顺序、生命周期清理仍有 13 分未验证；UI 媒体整体判定另有 3 分受取证基础设施影响。实际图标和音频已有正向证据，但截图/Slate 额外推进影响精确显示时长测量，不能判为该项完整通过，也不能直接判模型时长实现失败。

#### 场景效果：73/100，部分完成

**已完成：** 核心 Notify、Trace、精确上下文匹配、多条资源命中、加载和负向路径；双角色隔离；专用服务器无输出、客户端只输出一次；实质 FootStep 蓝图、地图/资源库/工厂配置；重复 Apply 后两个有效 Notify 的字段、数量和重新打开结果保持稳定。

**主要失败：** 保存的 Land 效果配置为 Walk，实际 Apply 也生成 Walk，属于候选配置错误。

**未验证边界：** 完整参数视听效果、原类型兼容、可见脚部位置/法线仍未验证。编辑器预览有正向证据，但配套游戏隔离试验没有形成正常 Hero 前后对照，因此不能判“预览无污染”通过，也不能反向认定已污染游戏。

**评价：** GPT-6 在这批交付中取得最高的已确认分数和覆盖率，多人交互、失效处理和场景效果主链路较完整。但仍不能直接交付为全功能完成，尤其要补配置变更、UI 排版、蓝图职责和 Pawn 生命周期。

**未验证归因：** 42 分未裁定中，37 分属于评测前提或观察不足，另有 5 分涉及选图等责任尚未厘清，保留归因不足。当前没有未知项被归为纯候选前置阻断，但这不等于没有模型缺陷：已确认失败的 41 分单独记录，不混入未知。

### 1.3 Claude Opus 5.5：部分完成，蓝图职责和部分编辑器流程较好

#### 交互：64/100，部分完成

**已完成：** Actor 和 ActorComponent 两类目标均有实际完整拾取证据；多人竞争、请求去重、归属隔离、遮挡和超距拒绝，以及持久化配置、蓝图和诊断信息。

**主要失败：**

- 目标 ASC 路径将物品交给目标所有者，归属不符合要求。
- 空接口场景出现实际崩溃。
- Tab 无法正常关闭界面并恢复输入焦点。
- 更换 Pawn 后仍沿用旧 Pawn 的扫描任务。

**未验证边界：** 三种配置变更的实际拾取均成功，但 Tooltip 没有触发或采集到所需 UI 名称证据，配置项因而未能完整裁定；另有界面和动作条件未形成的缺口。合计保留 24 分未验证，不能将这些缺口当作通过，也不能把所有缺口都归因于界面无法关闭。

#### 连杀荣誉：77/100，部分完成

**已完成：** 基础规则、网络分发、真实对局链路、数据资源和文档回归；Relay 的本地/远端分支以及 Host 的创建、播放和移除承担实质蓝图职责。

**主要失败：** 通知重放重复展示；高档替换时 Double 与 Triple 重叠；异常媒体资源后的合法后续流程出现崩溃；正常重生且新 Pawn 已就绪后，旧 Toast 仍显示。

**未验证边界：** 异步队列及完整 UI 媒体行为共 7 分受基础设施影响。录到的 MetaSound 音频没有充分证明来自指定资源，不能据此声称“声音正确”，也不能写成“静音”或“播错声音”。

#### 场景效果：74/100，部分完成

**已完成：** 核心匹配与资源主链路、保存的地图及第二资源库、实质蓝图和工厂；编辑器预览能按库、上下文、表面切换，并形成正常 Hero 前后游戏隔离的有效对照。

**主要失败：** Modifier 保存与应用的 Walk/Land 配置错误：Walk 生成 Land，Land 的原 2 个有效 Notify 变成 0 个。

**未验证边界：** Walk 的重复应用有非零稳定结果，但 Land 的 `0→0` 只能说明空结果没变化，不能证明有效 Notify 的重复 Apply 正确，因此完整幂等性仍未验证。完整参数视听、原类型兼容及脚部位置/法线同样存在缺口。

**评价：** Opus 的本次交付在部分实质蓝图和编辑器预览环节更完整，与 GPT-6 属于接近的完成度。它仍存在崩溃、输入焦点、荣誉清理和动画配置问题，不能把较少的确认失败权重直接解释为总体更可靠。

**未验证归因：** 53 分未裁定中，7 分是候选前置未打通，46 分是评测缺口。前者包括界面无法完成正常关闭与重开周期，及 Land 首次生成零个有效 Notify，使后续完整幂等性缺少非空基准；后者包括已拾取成功却未采到 Tooltip 名称、异步或视听取证不足。没有证据的部分仍不判成功或失败。

### 1.4 GPT-5.6 Sol：原始交付与荣誉最小修复后的结果

原始荣誉正常 Unity 构建失败的记录保留。经用户授权，助手仅在独立副本中修改两个 C++ 文件内四处 GameplayTag 标识符；没有修改标签字符串、业务逻辑、蓝图资产或构建配置。下列荣誉分数来自修复后的独立验收，交互与场景效果原样保留。

#### 交互与背包：9/100；确认失败 39，未验证 52

**已完成：** 原生组件负向安全处理、补充事件数据以及部分说明与边界记录有通过证据。

**主要失败：** 保存交付未完成 F/Tab、AbilitySet、物品模板和 UI 的持久接入。正常输入已到达 viewport/PlayerInput，目标在扫描范围内且独立碰撞命中，但没有形成生产能力、提示、拾取和背包闭环；死亡/更换 Pawn 后的后续交互也没有成立。

**未验证边界：** 缺少有效拾取正例时，不能把零库存、零提示或零成功次数当成遮挡拒绝、竞争去重及归属隔离通过。辅助 C++ 组件测试成功也不能替代正常 F 操作的生产接线。52 分未知保留。

原因按完整评分项标注；同一前置错误可能影响多项，所以表中权重不是独立错误数量。混合项不再拆成虚假的精确分值。“候选前置”只定位当前验证被什么挡住，不证明下游算法错误，也不意味着必须修改候选才能设计独立补测；“评测缺口”同样不证明候选通过。

- 固定同一客户端、代理、引擎和评测器版本；提前声明原始交付与最小修复后的结果是否分开统计，对四组执行相同政策。
- 正常输入后等待可观察的动作回执和状态条件，再开始计量；每条案例独立准备和复位，避免前一条失败造成后一条无法测。准备过程不能替候选补缺失业务。
- 截图与音频采样不额外推进业务 Tick；统一游戏、UI 和单调时钟，减少采样对显示时长的干扰。
- 用正常死亡、销毁、重生和切图验证生命周期，并记录旧/新对象和世界身份。未销毁旧 Pawn 的测试装置不能被误判成候选缓存泄漏。
- 完整采集 Walk/Land×三种物理表面的连续画面与可归属音频，分别判断资源正确、参数生效和实际视听表现。

### 3.2 在同一项目场景中增加更难的任务与隐藏变体

| 增强方向 | 具体测试 | 要区分的能力 |
| --- | --- | --- |
| 隐藏配置 | 运行前随机选取冻结种子：物品数量、图标、角色身份、库顺序、物理材质与时间阈值。 | 真正的数据与配置驱动，而非只对样例写死。 |
| 并发与异步 | 两玩家同帧争抢；相邻帧重复请求；异步加载乱序完成；荣誉高低档在同窗口到达。 | 服务器权威、去重、隔离、消息顺序和替换正确性。 |

### 3.3 从一次交付对比升级为可重复的模型评测

- 每模型每任务进行至少 3–5 次独立生成，固定预算、起点与提示，保留全部结果；将生成成功率和同一交付的重复运行稳定性分开。
- 单列原始交付首次构建/任务通过率、最小修复后结果、各维度得分和人工介入量；样本足够时报告离散程度及置信区间。
- 开发时间、工具与构建时间、网络/代理等待、令牌和计费分别记录，再比较效率。
- 保留当前 v2 作固定回归集；新增难题使用另一个冻结版本。先确定案例、权重和裁定规则，再运行更强模型，不按看到的结果调整分数或排序。
